# Independent V2 map geometry, shadow and security audit

Reviewer: delegated Codex numerical/code audit agent. The reviewer owned `src/buildings.ts`, `src/ShadowLayer.ts`, synthetic tests and this report. MapPanel/App/CSS, map integration, live network QA and publication remained with the implementation agent. No map tile corpus was downloaded or saved by this reviewer. Tests use authored synthetic polygons, not captured map tiles.

## Confirmed findings and fixes

1. **Critical — quadratic ring-signature allocation before limits.** The original deduplication routine materialized every forward/reverse cyclic ring permutation. An initial synthetic 30,000-vertex ring run exhausted the Node heap (approximately 4 GB) and exited in 11.5 seconds before the output cap. That pre-fix test was too large for the already identified unsafe path; subsequent executions used a 256 MB heap ceiling and ran the oversized case only after early guards were implemented. The same input is now rejected before clipping/canonicalization. Ring signatures use linear-time minimum rotation and exact coordinates; repeated growing union was replaced by one union per group.
2. **High — malformed input could disable the vertex budget.** Counting `ring.length` before validating the ring could add `undefined` and turn the global counter into `NaN`. Counters now change only after type/length validation. A malformed ring followed by 1,100 repeated 101-point footprints still hits the explicit 100,000-vertex budget, marks the model incomplete and never reports a clear ray.
3. **Medium — group identity and excessive deduplication.** A global footprint signature dropped features with different stable IDs, and centimeter rounding could collapse nearby distinct footprints. Deduplication now retains distinct valid stable IDs, groups parts only by ID plus height/base, and uses exact canonical geometry only for missing-ID deduplication. Duplicate parts within the same group are removed conservatively. Different tile fragments are unioned with holes and MultiPolygon parts preserved. Invalid/nonstable IDs fall back to geometry identity.
4. **Medium — spatial rejection was applied before local filtering.** Loaded source features can aggregate hundreds of far-away building parts. Bounded outer-ring bounds scanning now removes provably nonintersecting parts before local polygon/vertex validation and clipping. A 500-far-plus-one-near MultiPolygon fixture stays complete. Far degenerate rings do not invalidate the neighborhood; the equivalent defect near the selected point does. Separate scan budgets remain explicit; no cap was silently removed. Diagnostic `reasons` contains counts only.
5. **Medium — date-line bounds could span most of the world.** The boundary now uses unwrapped longitudes nearest the supplied origin, with a short west-to-east interval on both sides of ±180 degrees. Local Mercator conversion also wraps the shortest longitude difference. Tests verify short bounds centered on the original world copy, meter round trips and local clipping.
6. **Medium — incomplete or invalid ray inputs could appear clear.** Missing/incomplete models, nonfinite/out-of-range altitudes and mesh/part-count mismatches now return `insufficient`. An incomplete model takes priority over inside/hit/clear because the overall model is not established. A valid below-horizon sun returns the explicit night status. No generated midnight or clear result substitutes for missing geometry.
7. **Medium — caster roofs were clipped by the fixed shadow camera.** Fixed ±250-meter shadow-camera bounds could exclude 500-meter roofs at low sun, despite the ray test seeing those meshes. The shadow camera now fits the combined caster/ground bounds at each valid solar angle. Tests project all model bounds inside the actual camera frustum for 500-meter roofs at 0.1/10/45/89.9-degree altitude and each cardinal azimuth.
8. **Compatibility and containment.** Three 0.186 removed `PCFSoftShadowMap`; the layer now uses supported `PCFShadowMap`. Standalone invalid solar inputs do not poison the light position with `NaN`. Courtyard wall boundaries and a base exactly at the 1.6-meter observer height are classified conservatively as inside. A pin inside a ground-based footprint remains inside even under a low roof; elevated bases above eye height retain clearance. This footprint policy is separate from the ray's explicit 1.6-meter height.
9. **Offscreen repaint requests.** The design audit reported actual offscreen GL work when changing time. The custom layer now gates `setSun` repaint requests on its `active` flag while preserving current solar/light state and ray results. A direct production-layer mock test checks zero requests while inactive and one request when active. Intersection/visibility integration and actual browser GL draw counts remain with the integration/design auditors. Caps and walls use separate cream/darker materials; an actual production extrusion test verifies both material groups and unchanged ray intersections.

10. **GPU geometry budget.** The original 24,000-contour-point limit did not bound nonindexed extrusion geometry below 100,000 vertices. The output/group contour cap is now 8,192 closed points. For each simple polygon with holes, one-step no-bevel extrusion uses at most 12 times its closed-ring point count: cap triangulation plus six side vertices per open contour edge. Thus all building position buffers total at most **98,304 vertices**; the ground receiver adds four positions (six indices), leaving at most **98,308 position vertices**, or 98,310 with its indexed receiver expanded. The actual production-layer regression processes 48 synthetic parts each with three holes: 47 parts / 8,084 contour points produce **95,880 building positions / 95,884 scene positions**. The omitted 48th part sets incomplete and ray status insufficient. The 240-part cap remains.

## Boundaries and budgets

- Local model: square ±150 meters east/north; flat ground and Mercator scale at the selected origin.
- Output: at most 240 contour parts and 8,192 closed contour vertices, bounding production extrusion positions to 98,304 plus the four-position receiver. Any omitted output marks the model incomplete.
- Source scan: at most 10,000 features, 50,000 outer polygon parts and 1,000,000 outer vertices for bounded spatial filtering.
- Relevant geometry: 100,000 input vertices total; 2,048 points per ring; 8,192 per feature; at most 240 relevant polygon parts per feature and 128 rings per polygon. A group retains at most 960 fragments / 8,192 closed contour vertices before one union.
- Missing/invalid heights use conditional 9-meter tops; invalid bases use conditional zero. All live heights are cartographic estimates, including numerically valid provider values. Limits and invalid geometry are never presented as a complete clearance result.
- Rings are validated and normalized; degenerate rings are rejected. Polygon-clipping performs its own bounded-input boolean operations and may still be expensive on pathological intersection patterns. This report does not claim constant-time processing of arbitrary adversarial geometry.

## Coordinate and renderer review

The baseline SunCalc calculation is unchanged: degrees, clockwise from north. Local polygons use east/north; extrusion rotates them into **x east / y up / z south**. The actual exported production `mercatorModelMatrix` is tested against expected Mercator east/south/up directions and meter scale. The [official MapLibre custom Three.js example](https://maplibre.org/maplibre-gl-js/docs/examples/add-a-3d-model-using-threejs/) provides the Mercator custom-layer convention. This layer supports the Mercator city view, not a general globe projection.

Source review confirms use of MapLibre's existing WebGL canvas/context, `autoClear=false`, renderer state reset before and after a custom draw, and resource cleanup without forcing loss of the shared context. Geometry/materials and shadow targets are disposed. This is source-level shared-context review; synthetic Node tests do not emulate browser GL state. Browser rendering/context-loss/fallback checks remain in the integration/live audit.

The owned modules contain no tile fetch, cache, corpus persistence, telemetry, geolocation or dynamic HTML. They consume the supplied features in memory. Map style/tile requests and geocoding are controlled by the integration code and must be covered by its explicit privacy notice and live network checks.
